## P15 — Test planning

**Use when:** A change needs a risk-based verification strategy.

**Inputs:** Requirements, proposed diff, system boundaries and candidate environment.

```text
Plan evidence for [change]. For each important requirement or risk, identify the realistic failure to catch and the cheapest reliable test level. Include relevant happy, invalid, empty, denied, failure and concurrency cases. Specify fixtures, independent expected results, safe isolation, exact existing commands or missing setup, and candidate/environment identity. Distinguish manual, unit, integration and end-to-end checks; use regression/smoke labels by purpose. Avoid arbitrary test counts and redundant assertions. Return a Test Plan; do not claim checks ran. Also decide new automation versus manual/existing protection, suite membership, triggers, selection broadening, required task/integration/release gate and maintenance owner. Confirm the proposed test is discoverable and can detect its intended fault. Use QUALITY.md/W34 for recurring policy rather than duplicating it.
```

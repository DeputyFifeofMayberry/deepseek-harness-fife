## W28 — User Flow, Interaction States and Usability

**Purpose:** Turn an accepted requirement into an understandable complete interaction.

**Use when:** A new or confusing user workflow, consequential state change, or broader audience. **Skip when:** A minor correction whose surrounding interaction is already understood.

| Prompt | Your response |
|---|---|
| **Goal and audience**<br>User, task, requirement ID, first/repeat use; consequence of misunderstanding. |  |
| **Flow and alternatives**<br>Entry → actions/decisions → response → outcome; cancel, retry and interrupted paths. |  |
| **State map**<br>Relevant initial, empty, loading, populated, partial, success, error, denied or unavailable states; visible next action. |  |
| **Hierarchy and accessibility**<br>Primary/secondary actions, labels, navigation, keyboard/focus, error announcements and non-color cues. |  |
| **Prototype and question**<br>Sketch/mockup/interactive version; what it must establish and what it cannot establish. |  |
| **Observation script and evidence**<br>Goal without click instructions; participant/context, observations, help supplied and limitations. |  |
| **Disposition and acceptance**<br>Confusion → revision → recheck; linked requirements/tests; owner and remaining gates. |  |

**Close the worksheet when:** The flow and relevant states are agreed, significant usability/accessibility risks have checks, and actual observations are distinguished from planned tests. Implementation approval does not imply usability has been proven.

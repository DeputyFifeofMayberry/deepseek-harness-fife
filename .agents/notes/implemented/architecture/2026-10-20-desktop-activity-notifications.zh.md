# Agent 备注：Desktop 后台活动通知

Status: implemented

[English](2026-10-20-desktop-activity-notifications.md) | 中文

## 问题

用户把 Desktop 窗口关闭到托盘让任务继续运行时，除非重新打开窗口查看，否则无法得知任务已经完成或有审批在等待决策。社区反馈反复请求原生的完成与审批通知。此前外壳唯一发出过的原生通知是静默的强制更新提示。

## 决策

检测放在 Web 客户端，呈现放在 Electron 外壳。一个客户端插件观察会话目录中 Host 列出会话的 `running` 状态迁移，并包装审批 Remote Event 瀑布，通过新增的私有 IPC 通道上报 `task-complete`、`approval-request`、`approval-resolved`。主进程仅在产品窗口隐藏、最小化或失焦时发出原生通知，负责其生命周期（新审批请求替换旧通知、应答后关闭、焦点清除、点击恢复并聚焦），并以 `userData/desktop/settings.json` 的 `notifications` 开关控制——两类默认开启，完成静默、审批有声。

完成信号采用会话级 `running` 收敛，而不是逐回合的 `turn/end` 事件：存在排队或链式回合的会话在其驱动收敛时只通知一次；任何会话的首次观察只作为基线，因此启动、重连与目录替换不会伪造完成事件。上报仅用于呈现：外壳按发送通道的提前返回约定校验发送方，丢弃非法载荷，任何上报都不能授权操作。通知文案使用外壳语言，至多包含待审批的工具名，绝不包含工具参数或会话内容。[Desktop 参考](../../../../apps/desktop/README.zh.md#activity-notifications)负责面向用户的行为；[外壳配置决策](2026-10-08-desktop-shell-configuration.zh.md)仍是该设置文件所有权的先例。

## 已考虑的替代方案

**由 Host 通过私有控制通道推送。** Host 已经计算活动任务事实，但该通道是请求/响应模式；推送协议需要提升 `DESKTOP_HOST_PROTOCOL_VERSION`、改动捆绑运行时，并重复渲染器已经观察到的事实。窗口隐藏时渲染器仍在运行，隐藏窗口场景不需要 Host 参与。

**客户端逐回合观察 `turn/end`。** 聊天绑定只存在于已打开的会话视图，会漏掉后台会话；逐回合上报也会在链式运行中刷屏并需要防抖机制。会话级收敛与退出检查使用同一口径。

**渲染器使用 Web Notification API。** 它绕过外壳的抑制规则与文案，且渲染器无法在 Windows 上拥有原生通知身份。

## 后果

无需重新打开窗口即可看到完成的任务与待决策的审批，代价是一个小型客户端插件、一条发送通道和一个沿用更新提醒约定的提醒模块。审批包装器的组合顺序错误会静默禁用审批通知；插件组合在审批呈现器之前，并有顺序测试固定包装器的落定行为。隐藏窗口下的渲染器节流仍是运行时问题，由人工验收覆盖；系统专注模式无论如何都可能抑制通知。安装版 Windows 与 macOS 的通知归属与资质仍是发布要求；存在 `DSH_DESKTOP_APP_ID` 时，启动会将其应用为 Windows 的 AppUserModelId。
